# PostgreSQL query hardening, pending deployment

The changes address duplicate writes, incorrect local quota denials and stale cache producers. They add no database index, schema migration, service, connection pool or paid resource. Production was inspected read-only; no production SQL writes, DDL, code push or deployment occurred. The backend remains on PostgreSQL 17 with the existing four-query-connection pool and separate LISTEN connection.

## Evidence and measurement window

The sanitized production snapshot in `review/query-production-aggregate-snapshot.json` was observed at **2026-11-05 02:37:22.895 UTC**. Server PostgreSQL 17.11 started at **2026-11-04 22:58:48.156 UTC**. The original inspection did not read `pg_stat_statements_info.stats_reset`; statement counters are cumulative since their collector reset, whose exact time is unavailable. Server startup is a separate timestamp and does not establish the statistics window. These aggregates provide mean, standard deviation, minimum and maximum, not p95/p99.

The snapshot estimated 478 live `records` rows, 2,269 updates and zero HOT updates. Physical storage was 294,912 bytes of heap, 131,072 bytes of table indexes and 58,261,504 bytes of TOAST relation storage including its indexes. Quotas recorded 5,270 updates, all HOT. The dominant record UPSERT had 2,735 calls, mean server execution 5.100 ms, maximum 394.404 ms, standard deviation 13.846 ms and 97,193,608 cumulative WAL bytes. It read one shared block and otherwise mostly hit shared buffers. No active lock wait was observed in that inspection. This supports investigating large JSON/TOAST update work; physical TOAST size alone does not prove bloat, and an empty wait snapshot does not prove contention never occurs.

The paired synthetic A/B experiment is separately documented in [query-optimization-benchmark.md](query-optimization-benchmark.md), with all observations and sanitized plans in `review/query-optimization-benchmark.json`. It used isolated local databases, 256 and 100,000 rows, four payload profiles, five warmups and 41 measured trials per variant. Its measured p50/p95 values describe those local trials, not production percentiles or projected savings.

## Implemented changes

**Exact duplicate record writes:** `save(item,true)` retains the existing UPSERT behavior but updates only when JSONB payload or expiry differs. JSON key ordering alone does not create a new tuple. Changed payloads and TTL changes are still written; strict `put` still reports a duplicate as a conflict. In the 100,000-row / 32-KiB high-entropy duplicate fixture, baseline p50/p95 was 0.602/0.683 ms with about 36,448 WAL bytes per attempt; the plain guard measured 0.119/0.145 ms and 54 bytes. The guard still locks the conflicting row and can emit lock WAL. It is not a zero-I/O or zero-contention operation.

The measured equal-payload CASE can preserve a TOAST pointer when only the SQL expiry changes, but it is **not adopted** in this stage. Existing payloads embed `expires_epoch`, and cache values often include a new retrieval timestamp, so real refreshes can change the JSON as well. CASE also increased CPU cost for changed payloads in the experiment. No TTL normalization or frozen-journal format change was introduced.

**Database-authoritative quota decisions:** the key-only 60-second denial map was removed. It could incorrectly deny a smaller admissible amount, a raised limit, an expired window, an external refund or capacity restored by rollback. A local cache cannot reliably observe distributed refunds and transaction rollback. Each `consume` now makes its existing atomic SQL decision. The validated first insert still requires `amount <= limit`; the existing conflict guard still receives `limit-amount`. There was no missing quota-overrun fix.

Accepted consumes deliberately retain their existing sliding-expiry semantics. For date-bearing daily/monthly keys, the date identifies the accounting period while the TTL retains the row afterward. This change does not reinterpret all TTLs as fixed windows. Repeated denials now cost database requests: the local four-worker benchmark measured hot-key round-trip p95 5.052 ms versus 2.850 ms across four distinct exhausted keys, with no admitted requests. Existing edge admission limits, application quotas and the four-connection pool remain in place; no extra metadata query or denial-cache invalidation service was added.

**Actual-clock deadlines:** record freshness, quota reset decisions and lease expiry use `clock_timestamp()` where wall-clock expiry is required. A conflicting lease assigns its new deadline in the post-lock UPDATE rather than reusing `EXCLUDED.expires_at`, which was computed before waiting. A controlled 350-ms lock wait with a 200-ms lease verifies that the acquired lease still has usable lifetime afterward. Long-transaction tests separately verify record expiry, quota reset and new lease lifetime against actual time. [PostgreSQL time semantics](https://www.postgresql.org/docs/17/functions-datetime.html).

**Fenced cache publication:** after acquiring a refresh lease, `cached` checks the cache again before charging upstream work. Cache publication locks the lease row in one materialized step, then checks its current owner and wall-clock expiry in a separate step before writing. Both the final cache record and optional producer-side records use this fence. An expired producer cannot overwrite a fresh successor, and an old release cannot delete the successor's lease. If a successor already published, the older caller receives that retained value; otherwise a typed local-refresh error is returned. The producer callback can optionally use `publishRecord` for side records such as the X cursor; existing callbacks can ignore this additive context.

Local `CACHE_LEASE_LOST`/`CACHE_LEASE_BUSY` coordination errors are distinct from upstream provider throttling. The social integration preserves the newest fenced cursor and does not set a shared provider cooldown merely because another process owns the refresh. Failed X budget reservations are not cached as a successful 30-day account lookup. Quota reservations still charge actual upstream work; fencing does not refund requests that were already made. Existing assistant reservation/refund transactions remain atomic and fail closed.

## Index decision

The existing `records_pkey(pk,sk)` supports leading `pk` lookups as well as the exact key reads used by `get`. A separate `pk` index is narrower but duplicates storage and adds write maintenance. At 100,000 synthetic rows it added 7,839,744 bytes and gave no consistent benefit across exact, prefix and ordered journal queries. No new index, fillfactor adjustment, autovacuum setting or feature flag is justified by the reported ten-percent planner estimate alone. [PostgreSQL multicolumn indexes](https://www.postgresql.org/docs/17/indexes-multicolumn.html).

## Validation and reproduction

Ten actual local query regressions cover no-op tuple identity, changed JSON/expiry writes, weighted concurrent quota admission, varying request amounts/limits, expiry/refunds/rollback, sliding TTL, post-lock lease deadlines, stale-owner release, stale cache/side-record publication, typed refresh contention, delayed miss rechecks and long transactions. Five of the initial six cases failed against the baseline; sliding TTL already passed and was preserved. The revised cases pass. Existing store, assistant reservation/refund and commit-notification integration tests also pass.

Root's final combined verification, including typed busy-error coverage, used the separate disposable `query_runtime_test` database: **292 JavaScript tests passed with two intentional opt-in skips, plus 10 TypeScript tests passed; 302 total passed, zero failed.** Type checking also passed. The model/vector opt-in tests are outside this SQL change.

To reproduce local tests, supply only a loopback disposable `MARKET_TEST_DATABASE_URL` ending in `_test`, then run `node --test tests/postgres-queries.test.mjs tests/postgres.test.mjs tests/assistant-budget.test.mjs tests/runtime-database.test.mjs` from `web/`. Never point integration tests or EXPLAIN ANALYZE writes at production. The benchmark CLI additionally rejects the in-use `engineering_test` database and cleans up only its own isolated schema.

For approved read-only operational inspection, supply backend-only `DATABASE_URL` and the appropriate `DATABASE_CA_CERT` privately, then run `node tools/inspect_postgres_queries.mjs` from `web/`. The inspector uses `BEGIN READ ONLY`, bounded statement/lock timeouts, fixed catalog/aggregate queries and optional statistics-reset inspection. It excludes application rows, payloads, SQL text, bind values and credentials. Do not paste private connection settings into reports or shell history. Availability of aggregate statistics depends on existing database privileges; the tool does not grant privileges or change the database.

The inspector now checks existing schema `USAGE` and statistics-view `SELECT` privileges through PostgreSQL catalogs before each optional statistics read. Restricted roles report `insufficient_existing_privileges` without deliberately triggering SQLSTATE 42501. The reset view is checked separately; permission revocation races still roll back to a read-only savepoint. Use an already authorized monitoring connection when aggregate statistics are needed, rather than granting monitoring privileges to the application role merely to run this diagnostic. Short successful `supabase_admin` sessions ending with SQLSTATE 00000 are normal disconnections, distinct from failed application connections.
